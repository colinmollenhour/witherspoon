# Course Review

Read an existing course as a first-hour learner and make it easier to start and finish. This is
not a new course and not a rebuild.

A user who reached this skill has a `course.json` tree on disk. If they do not, stop and say so.

## Non-negotiables

1. **Do not start a new course.** No interview, no spine from scratch, no fan-out of topic writers.
2. **Diagnose before you edit.** Invoked review has one gate: show the verdict, wait, then apply.
3. **No new facts.** Cuts, moves, and rephrases only. A number, API, or claim not already in that
   topic's Grounded facts or `SOURCES.md` is fabrication — the same rule generation uses.
4. **Do not change the syllabus unless asked.** Folding a satellite into a sidebar is an edit.
   Deleting a topic is a syllabus change.
5. **Address the user, not the machinery.** They have a folder of lessons. A line they will read
   names no skill, no tool, no gate, and no contract.

## Pipeline

### Stage 0 — Find the course

Locate `course.json`. Search the working directory and one level down. One match: use it. Several:
show titles and paths, ask which. None: ask where the course folder is. Missing or unreadable
`course.json`: stop.

### Stage 1 — Load the rubric

**Read `learner-pass`.** From `../course-builder/references/learner-pass.md` beside this skill if
that file is on disk, or by fetching `learner-pass` through a reference tool such as
`witherspoon_reference`. That document is the checklist, the finding shape, the apply constraints,
and the in-pipeline vs invoked-review split. This skill is the invoked-review caller: **you wait.**

Also skim `../course-builder/references/quality-gates.md` (or fetch `quality-gates`) so you can
re-check anything you touch in Stage 3. Do not run the full gate list before you have findings.

### Stage 2 — Diagnose

Follow `learner-pass` Phase 1. Walk the handoffs first — it is cheap and it is how you see
compression:

```
for each topic contract:
  FAIL the topic-as-topic if Inherits == Leaves
```

Then read the home copy, Unit 1 in order, every `brief.md`, and two later readings. On the home
copy, apply the skeptic test from `course-builder/references/spine.md` §4: a title that summarises
the mechanism, or a subtitle whose payoff an app the learner already has could deliver, is selling
the demo instead of the power — a finding, same as any other.

Write findings the way `learner-pass` specifies. End with the verdict. Then state exactly:

> I have not changed any files. Tell me what to apply — all of it, only the first item, or
> something else — and I will make those edits.

Then end the turn with the **Second pair of eyes** prompt from `learner-pass.md`. Print it for
them to copy. Do not answer it yourself.

Stop. Do not start Stage 3 in the same turn.

### Stage 3 — Apply

Only after a clear go. Apply the agreed items under the `learner-pass` constraints. Re-run the
views and widget check if a runtime exists, then every quality gate whose files you changed.

If the user asked to change the outline (merge two topics, drop a satellite for real), do that
explicitly and say the syllabus changed. Do not slip a deletion through as a wording fix.

### Stage 4 — Report

```
Reviewed: <course title> — <N> units · <N> topics · <N> projects
Applied: <what you changed, or "nothing — waiting">
Left alone: <the strong parts you named>
Next: the material is ready to look at. If they already have a website, offer to rebuild it
      so the pages match. Do not rebuild unless they ask.
```

**Address the user, not the machinery** in that last sentence: they cannot run a skill or a tool.

## Notes

- A first-hour problem in Topic 1 is worth more than a polish pass over Unit 5.
- Isolated writers produced the bloat; one editor who can see the whole tree is what undoes it.
- If the course was generated by an older pipeline, expect ledger quotes, three-platform
  restatement, briefs over 1,200 words, and seminar voice (journal citations, competitor
  catalogues, prosecuting the textbook). Those are the usual first cuts.
