## Question 1

**Type:** MULTIPLE_CHOICE

You mean to serve your site, but you `cd ~/projects` instead of `cd ~/projects/first-site`, then run
`python3 -m http.server 8000`. `~/projects` contains the folder `first-site` and no `index.html` of its
own. You visit `http://localhost:8000/`. What loads?

- Your page, because the server searches subfolders for an `index.html`
- A clickable list of the names inside `~/projects`, including `first-site`
- A `404`, because there is no `index.html` at that path
- Nothing — the server refuses to start without an `index.html` present

**Correct option index:** 1

**Explanation:**

The server serves one folder — the one you were standing in — and "The request is
mapped to a local file by interpreting the request as a path relative to the current working
directory." `/` maps to `~/projects`, which has no index page, so the documented fallback applies:
"otherwise a directory listing is generated." You get a list of names, and clicking `first-site` would
then reach your page. The first option imagines a search through subfolders; the server does no such
thing, it checks that one directory for `index.html` or `index.htm` and stops. The `404` option
confuses "no index page here" with "nothing here" — a directory listing is a `200`. And nothing about
starting the server depends on an `index.html` existing; the banner prints either way (objective 10).

## Question 2

Your server terminal shows this line, which appeared the moment you pressed Enter in the browser:

```

```

State what you did to cause it, what the server sent back, and what the final `-` tells you about the
size of the response.

address is `127.0.0.1`, loopback. The server looked for `nope` inside the folder it is serving, did not
find it, and answered `404`. The trailing `-` tells me nothing about size: this server always writes
`-` in that field, so a `-` there is not evidence that the response was empty.

**Sample answer:**

I asked for the path `/nope` with a `GET`, from this same machine — the client
address is `127.0.0.1`, loopback. The server looked for `nope` inside the folder it is serving, did not
find it, and answered `404`. The trailing `-` tells me nothing about size: this server always writes
`-` in that field, so a `-` there is not evidence that the response was empty.

**Explanation:**

A strong answer covers three things: that `GET /nope` is the request the learner themselves
generated by typing a path, that `404` is the server's answer and not a crash, and that the final `-`
is a permanent placeholder rather than a byte count. The tempting misreading is that `-` means "zero
bytes sent" — but the 404 page has a body, and that field is `-` on a `200` too. The other tempting
misreading is that `HTTP/1.1` in the quoted request line is the server's version; it is the client's,
echoed back, while the response itself is `HTTP/1.0` (objective 11).

## Question 3

**Type:** TRUE_FALSE

When you double-click `index.html` and it opens at
`file:///home/you/projects/first-site/index.html`, the browser still receives a `200 OK` — DevTools
just does not have a server to show it next to.

**Correct answer:** false

**Explanation:**

There is no `200` to hide. A status code is a server's verdict on a request, and over
`file://` no request was ever made: the browser opened the file off your disk the way a text editor
does. Nothing answered, so there is no status line and no response headers at all. Load the identical
file at `http://localhost:8000/index.html` and all of it appears — `HTTP/1.0 200 OK`, `Server:`,
`Date:`, `Content-type: text/html`, `Content-Length: 31`, `Last-Modified:` — because this time a
program was asked a question and replied (objective 12).

## Question 4

**Type:** MULTIPLE_CHOICE

Your laptop is serving your page and loads `http://localhost:8000` perfectly. You pick up your phone,
confirm it is on the same Wi-Fi, and type `http://localhost:8000` into its browser. It fails. What did
your phone try to connect to?

- Your laptop, which received the request and refused it
- Your Wi-Fi router, which does not run a web server
- Itself — `localhost` names whichever machine is doing the asking
- Your laptop, because `localhost`, `127.0.0.1` and `0.0.0.0` all name the same shared machine on a network

**Correct option index:** 2

**Explanation:**

`localhost` is not the name of your laptop; it is the name each machine uses for
*itself*. Your phone resolved it to itself, looked for something listening on port 8000 on the phone,
found nothing, and stopped — no packet ever left the phone, which is why your laptop's log shows no
line for the attempt. The first option assumes the request arrived and was rejected; it never arrived.
The second invents a hop through the router that `localhost` never makes. The fourth is the most common
version of this mistake — treating `localhost`, `127.0.0.1` and `0.0.0.0` as interchangeable names for
one machine everybody shares — and it is the reason people spend hours re-checking a server that was
working the whole time. What your laptop needs is a name that means *your laptop* from somewhere else,
and it does not have one yet (objective 10).

## Question 5

**Type:** MULTIPLE_CHOICE

You run `curl -I http://localhost:8000/index.html` against your real file and get
`Content-type: text/html`. A classmate renames their file to `home.html`, runs `curl -I
http://localhost:8000/` against the folder, and gets `Content-type: text/html; charset=utf-8`. What
explains the difference?

- Your classmate's file is saved in a different text encoding from yours
- Your classmate got the generated directory listing, and pages the server writes itself carry the charset; files read off disk do not
- `curl -I` reports the charset only when a request returns more than one file
- Your server is older than theirs and omits the charset

**Correct option index:** 1

**Explanation:**

With no `index.html` present, `/` produced a directory listing — a page the server
composed on the spot — and those generated pages carry `Content-type: text/html; charset=utf-8`. A real
`.html` file read off disk gets `Content-type: text/html` with no charset at all. Nothing about the
file's own encoding is involved, which rules out the first option: the server never inspects the bytes
to decide, it applies a type based on the extension and adds a charset only to what it generates
itself. `curl -I` asks for headers only and does not change them based on how many files are involved.
And both learners are running the same server — the difference is *what was served*, a stored file
versus a generated page (objective 12).
